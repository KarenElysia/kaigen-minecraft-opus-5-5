# 計画: 柔軟なコンテンツ制作と 2〜5 人マルチプレイ

作成日: 2026-11-08 / 対象ブランチ: `claude/project-thread-vm86dc`
位置づけ: ROADMAP の Phase 2（技術設計）に入る前の検討メモ。実装は承認後に行う。

## 0. 前提と制約

- AGENTS.md のハードルール: libc 禁止、グローバル禁止、printf 禁止、ロックステップ（全レーンが `app_init` / `app_update_and_render` を実行）。
- エンジン（`hz/` の向き先の `src/engine/`、`src/lib/`、`src/os/`、`shaders/`）は読み取り専用。必要な変更は触らずに報告する。
- ROADMAP では「マルチは保留」（Phase 4）。マルチを前倒しするかはユーザーの判断事項。
- ゲームルールの追加、マネタイズ、公開方針はユーザーに確認する（CLAUDE.md）。
- 性能予算: デスクトップ 60fps、モバイル 30fps。通信とコンテンツ追加は前後の F3 計測を OPTIMIZATION_LOG に残す。
- 現状の WebCraft は ECS を使っていない（`src/webcraft/` は独自のワールドと構造体）。アセットは無く、テクスチャ・音は起動時に手続き生成している（TECHNICAL_ARCHITECTURE.md）。

### 0.1 公式ガイドとの対応（https://kaigen3d.com/docs/writing-applications）
- アプリの書き方は公式ガイドと一致している。`src/webcraft/wc_game.c` は `hz_app_config`、`app_init`、`app_update_and_render`、`app_state_size` を使っている。
- 並列化の 4 段階（ECS → レーンカーネル → `lane_range` → `is_main_thread()` の 1 レーン限定）のうち、WebCraft は独自のジョブ方式（`WcJob`、`wc_world.c`）と `lane_range` を使っている。
- ガイドは ECS を最初に勧めている。ネットコードの案 A（ECS 移行）はこの推奨と合うが、作業量は大きい。
- ガイドにはビルド手順、ファイル構成の詳細、アセットの扱いが無い。これらは別ページの想定で、未確認。
- コンテンツのデータ化（`HZ_REFLECT` の構造体を読み込む方式）は、ガイドの「ヘッダを読んで使う」方針と合う。

## 2. キャラクターとオブジェクトを柔軟に作るための要素

### 2.1 データ駆動のコンテンツ定義（最優先）
- ブロック・アイテム・モブ・クラフトレシピを、コードではなく **データ** として定義する。
  - 方法: `HZ_REFLECT()` 付きの構造体を `.h` に置き、エンジンのリフレクションで読み込む（エンジンの codegen が使える）。
  - 理由: 種類を増やすたびにコードを書き換える必要がなくなる。`--commands` の `set:` で実行中に値を変えて試せる。
- 定義ファイルの置き場: `assets/` 配下に `wc_blocks.hzt` のような形式で置き、`hzproject.hzt` の `asset_roots` に含める。
- 注意: 現在の `WC_BLOCK_LIST`（約 160 種）はコードに直書きされている。移行は段階的に行い、描画・生成の結果が変わらないことを定点スクショで確認する。

### 2.2 キャラクターとモブのモデル
- 作成フロー: Blender（または他の DCC）→ glTF / GLB で書き出し → `hzbuild cook` → 実行時に読み込み。
- 必要なもの:
  1. **骨格の規約**: 人型の関節名と役割（頭・胴・腕・脚）を決め、リターゲットのプロファイルを作る（retarget.md）。
  2. **アニメーション規約**: 待機・歩行・攻撃・被ダメージ・死亡の名前を統一し、ステート機械で切り替える（character.md の STATES）。
  3. **見た目の規約**: ボクセル風か、ローポリか。WebCraft の手続きテクスチャと合う見た目を決める（ユーザーに確認）。
- 作業の分担案: 形と骨格は外部ツールで作り、挙動（AI・当たり判定・ステータス）はデータとコードで書く。

### 2.3 オブジェクト（家具・装置・構造物）
- 小さな物は glTF、ブロックに近い物は既存のボクセル生成（`wc_gen.c` 系）に寄せる。
- 当たり判定は見た目と分けて定義する（コリジョンは専用の形状データ）。

### 2.4 ツール整備
- 定点スクショ用の `--commands` スクリプトを `tests/` に置く（Phase 0 の残タスク）。
- コンテンツの検証を自動化する: データファイルの読み込み失敗、骨格名の不一致、ID の重複を、ビルド時にエラーとして出す。
- ホットリロードの要否: 最初は不要とし、`--commands` と再起動で回す。必要になったら engine の `editor` を使うかを検討。

## 3. 2〜5 人マルチプレイに必要なもの

### 3.1 設計の方針（最初に決めること）
1. **権威はホストが持つ**: 1 人がホストとなり、ワールドの状態（ブロックの編集、モブ、他プレイヤーの結果）を決める。ホストも 1 人のプレイヤーとして遊ぶ（エンジンの `--host` と同じ形）。
2. **地形は同期しない**: ワールドは「シード＋編集履歴」で決まる（`WcEditStore`）。参加時は編集の差分だけを送り、地形は各自が生成する。これが通信量を抑える鍵になる。
3. **入力を送り、結果を受け取る**: クライアントは入力（移動・操作）だけを送る。ホストが判定し、状態を配る（エンジンのネットコードの基本モデル）。
4. **RPC は例外**: 攻撃や被ダメージなどのゲームプレイ結果は状態として配り、RPC は使わない（netcode.md の方針）。

### 3.2 ネットコードの組み込み方（決定が必要）
WebCraft は ECS ではないため、エンジンのネットコードをそのまま使うのは難しい。選択肢は次の 3 つ。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A. ECS へ移行 | ワールドとプレイヤーを ECS に置き換え、`ecs_netcode_init` を使う | エンジン標準の予測・補間・ghost がそのまま使える | 作業量が大きい。既存コードの大半に触る |
| B. 構成要素だけ使う（推奨、ガイドの「ECS 優先」と異なる点は 0.1 参照） | `NetcodeServer` / `NetcodeClient` と `NetcodeServerLink` / `NetcodeClientLink` を、ECS を使わずに直接呼ぶ | 既存コードへの影響が小さい。予測・入力検証・チケットは使える | ghost の登録と差分送信を自前で書く部分が出る |
| C. 独自プロトコル | `NetHost` の上に独自のメッセージを載せる | 最も自由 | 予測・再送・入力検証を全部自前で作る。エンジンの仕組みと二重になる |

推奨は B。理由: 通信量（プレイヤーの位置・入力・編集差分）が少なく、予測と検証の仕組みをエンジンから借りられるため。B の具体的な作業は次の通り。
- ghost 型: プレイヤー（位置・向き・状態）とモブ（位置・体力）の 2 種。
- 編集差分: チャンク単位の大きなデータは「huge ghost」（信頼性のあるブロック送信）として送る（netcode-replication.md）。
- 入力: 移動キーと視点、操作（設置・破壊）をイベントとして送る（netcode-input-rpc.md）。

### 3.3 通信路と接続
- ネイティブ（PC）: UDP または QUIC。同一 LAN なら直接接続。
- ブラウザ: WebSocket または WebRTC データチャネル。
- インターネット越し: ICE（STUN / TURN）で NAT を越える。TURN サーバーの用意が必要（運用コストが発生するため、ユーザー判断）。
- 参加方法: 接続チケット（hex 文字列）を共有する。最初は手動でコピー、後に招待リンク。
- 認証: 友人内なら接続トークンだけで足りる。公開するなら ID 認証（Kaigen Online か別の仕組み）が必要。ここは公開方針と連動するためユーザーに確認する。

### 3.4 同期が必要なもの（優先順）
1. プレイヤーの位置・向き・アニメーション状態（補間で滑らかに見せる）。
2. ブロックの編集（設置・破壊）。ホストが受理したものだけを反映する。
3. モブの位置・体力・状態（ホストだけが動かす）。
4. インベントリ（プレイヤーごとに持ち、ホストが検証する）。
5. 時間・天候（ホストの時計に合わせる）。

### 3.5 性能と検証
- 通信量の目安（想定）: プレイヤー 5 人 × 20〜30 回/秒 × 数十バイト。通常の遊びでは小さい。ただし編集の一斉送信（大量のブロック破壊）は負荷になるため、差分をまとめて送る。
- 検証:
  - 同一マシンで `--clients N` を使い、2〜5 人の動作を確認する（エンジンの開発用起動）。
  - `--bots N` で負荷試験を行う（netcode-loadgen.md）。
  - 通信の遅延・損失は `net-sim.md` の模擬で再現する。
- 性能: F3 の計測値を前後で OPTIMIZATION_LOG に記録する。モバイルは単一スレッドのため、通信処理を毎フレームの重い処理にしない。

### 3.6 段階
| 段階 | 内容 | 完了条件 |
|---|---|---|
| M0 | 単一プロセスで「ホスト＋クライアント 2 人」を `--clients 2` で動かす。ネットコードの構成要素（B 案）の接続だけ確認 | 2 人で同じ位置を見られる |
| M1 | プレイヤーの移動同期と補間 | 遅延 100ms でも動きが破綻しない |
| M2 | ブロックの編集同期と、後から参加した人への編集差分の送信 | 途中参加で編集が一致する |
| M3 | モブの同期（ホストだけが動かす） | 2 人以上で同じ敵を見て攻撃できる |
| M4 | 招待（チケット）、切断・再接続、5 人での負荷確認 | 5 人で 30fps（モバイル）、60fps（PC）を維持 |

## 4. 作業の進め方（提案）

1. **Phase 0 の完了**: `tests/` と定点スクショ用スクリプトを作る（残タスク）。これがないと以降の検証ができない。
2. **Phase 2（技術設計）**: 次の 3 点をユーザーと決めて TECHNICAL_ARCHITECTURE.md に書く。
   - ネットコードの方式（A / B / C。推奨は B）。
   - コンテンツのデータ形式（2.1）。
   - マルチを今すぐ進めるか、Phase 4 の予定どおり後にするか。
3. **Phase 3〜4**: M0 から順に進める。各段階の終わりでユーザーの承認を得る。

## 5. エンジン側で必要になる可能性がある変更（触らずに報告する）

- ECS を使わない場合の ghost 登録の補助関数が不足していれば、エンジン側への要望として報告する。
- ブラウザの埋め込みアセットの読み込み方法（書き込みなし環境での取り込み）は、要検証。
- モバイル（単一スレッド）でのネットコードの動作条件は、エンジンの wiki に明記がないため、要確認。

## 6. ユーザーに確認したいこと

1. マルチプレイを今の Phase 4 のまま後回しにするか、前倒しするか。
2. ネットコードの方式（A: ECS 移行 / B: 構成要素のみ（推奨） / C: 独自）。
3. 公開するか。公開する場合は ID 認証と TURN サーバーの運用が必要になる。
4. 見た目の方向性（ボクセル風 / ローポリ / 既存のブロック調）。
5. コンテンツのデータ形式（2.1）を今すぐ導入してよいか。既存のブロック一覧の移行を含む。
